# Dashuri Reels — database and API (EXPERIMENT)

## 1. Database

**Migration:** `supabase/migrations/20261123000100_reels_experiment.sql`. It is new and forward-only. No existing migration was edited, and it has never been run against any hosted database.

Everything is in a new **`reels`** schema. Existing tables are only referenced (foreign keys to `identity.accounts`) and read by the API (`identity.profiles`, `hosting.hosts`, `safety.blocks`, `identity.consents`, `calls.calls`). None is altered.

### What was reused instead of duplicated

| Proposed entity | Decision |
|---|---|
| `creator_profiles` | **New, minimal:** only `bio`. Name, photo and languages come from `identity.profiles` / `profile_photos`. Host status comes from `hosting.hosts` |
| `reels_videos` + `reels_video_assets` | **Merged into `reels.videos`.** There is one asset per video (the provider holds renditions), so a second table would only duplicate keys |
| `reels_likes`, `creator_follows`, `reels_views`, `reels_reports` | **New:** `reels.likes`, `reels.follows`, `reels.views` (one row per viewer, video and day), `reels.reports` (one per reporter per video) |
| `reels_moderation_cases` | **New:** `reels.moderation_cases`, plus the append-only `reels.moderation_decisions` and `reels.appeals` |
| `reels_feed_events` | **New:** `reels.feed_events` (product analytics, consent-gated) |
| Blocks | **Reused:** `safety.blocks`. Blocking a creator uses the existing `POST /v1/blocks` |
| User reports and enforcement | **Kept separate:** reel reports target content, not a person. Account-level enforcement (suspend/ban) stays in the existing safety queue |
| — | `reels.provider_webhooks`: webhook dedupe (hash only, no payload) |

### Tables

| Table | Key columns | Notes |
|---|---|---|
| `creator_profiles` | `user_id` PK → accounts, `bio` ≤ 300 | |
| `videos` | `id`, `creator_id`, `caption` ≤ 300, `language`, `declared_duration_ms` (15–60 s), `duration_ms`, `status` (9 states), `rejection_code`, `provider`, `provider_upload_id` UNIQUE, `provider_asset_id` UNIQUE, `playback_id`, counters, `evidence_hold_until`, `media_purged_at`, `published_at`, `deleted_at` | Checks: published ⇒ `published_at`; deleted ⇒ `deleted_at` |
| `moderation_cases` | `video_id`, `source` (automated, report, appeal, provider_unavailable), `status`, `priority` 1–5, `automated_scores` jsonb | **One open case per video** (partial unique index) |
| `moderation_decisions` | `video_id`, `case_id`, `decision` (approve, reject, remove, restore), `reason_code`, `note`, `source` (automated or moderator), `decided_by` | **Append-only** (trigger, and UPDATE/DELETE revoked). A moderator decision requires `decided_by` |
| `likes` | PK (`video_id`, `user_id`) | Idempotent |
| `follows` | PK (`follower_id`, `creator_id`), no self-follow | Idempotent |
| `views` | PK (`video_id`, `viewer_id`, `day`), `watched_ms`, `completed` | Idempotent counting and the "seen" signal |
| `reports` | UNIQUE (`video_id`, `reporter_id`), 10 categories | |
| `appeals` | UNIQUE `video_id` | One appeal per reel |
| `feed_events` | `user_id`, `event` (10 names), `video_id`, `creator_id`, `value_ms`, `session_id` | No free text |
| `provider_webhooks` | `delivery_hash` PK | |

**Indexes for feed queries:**
- published (`published_at desc, id desc`) where published;
- per creator (`creator_id, created_at desc, id desc`);
- pending (`status, updated_at`);
- purge;
- moderation queue (`status, priority, created_at`);
- likes and views by user;
- follows by creator;
- events by type and by CTA (`user_id, creator_id, created_at`).

**Publication guard (fail closed).** Trigger `reels.guard_publication`:
- new rows must start as `awaiting_upload`;
- `→ published` requires the latest decision to be `approve` or `restore`;
- a deleted reel cannot be revived.

**Access control.** For all 11 tables:
- RLS is enabled **and forced**;
- policy `service_all` applies to `api_service` and `worker_service` only;
- `anon` and `authenticated` are revoked.

Unapproved videos are therefore never reachable through PostgREST or Realtime. This is tested: both client roles get `permission denied`.

**Deletion.**
- **Creator delete:** status `deleted`. Media is purged by the job, unless a report, an open case or a rejection exists, in which case a 90-day evidence hold applies.
- **Account deletion:** the existing job anonymises the account; `reels-account-cleanup` then deletes its reels, likes and follows and clears the bio.
- **Kept for audit:** reports and decisions (ids only).

**Rollback.** `docs/reels/experiment/drop_reels_schema.sql` runs `drop schema reels cascade`. No existing object depends on it.

## 2. API (v1, additive)

Also in `api/openapi/dashuri.v1.yaml` under the `reels` tag: 17 paths and 25 schemas, generated by `docs/reels/experiment/openapi_reels.py`.

**Common rules:**
- Every endpoint returns `503 reels_disabled` while `REELS_ENABLED=false`.
- Callers must be 18+ (`409 not_age_eligible`).
- Writes need an unrestricted account (`409 account_restricted`).
- Errors are RFC 9457 problem+json, as before.

| Method | Path | Request | Response | Notes |
|---|---|---|---|---|
| GET | `/v1/reels/config` | — | `ReelsConfig` | `uploads_available` is false without provider credentials |
| GET | `/v1/reels/feed` | `?tab=for_you\|following&cursor&limit≤20` | `Page<Reel>` | Published only; blocks and own reports excluded |
| POST | `/v1/reels/uploads` | `{caption?, language?, duration_ms}` + **Idempotency-Key** | `201 {reel, upload_url, expires_at}` | `503 video_provider_not_configured`; `409 reel_upload_limit` (10/day, race-safe) |
| GET | `/v1/reels/{id}` | — | `Reel` | Others see it only when published and not blocked |
| DELETE | `/v1/reels/{id}` | — | 204 | Creator only (404 otherwise) |
| PUT | `/v1/reels/{id}/like` | `{liked: bool}` | `{liked, like_count}` | Idempotent |
| POST | `/v1/reels/{id}/share` | — | `{url, text}` | Counts the share |
| POST | `/v1/reels/{id}/reports` | `{category, details?}` + Idempotency-Key | 204 | Repeat is a no-op; `409 self_report` |
| POST | `/v1/reels/{id}/appeals` | `{statement}` + Idempotency-Key | 204 | Rejected or removed only; once (`409 already_appealed`) |
| POST | `/v1/reels/events` | `{events: [≤50]}` | 202 | Client events only (6 names) |
| GET | `/v1/creators/{userId}` | `me` allowed | `CreatorProfile` | 404 when blocked either way |
| GET | `/v1/creators/{userId}/reels` | `cursor`, `limit` | `Page<Reel>` | All non-deleted statuses for `me` |
| PUT | `/v1/creators/{userId}/follow` | `{following: bool}` | `{following}` | Idempotent; `409 self_follow` |
| PATCH | `/v1/me/creator` | `{bio}` | `CreatorProfile` | |
| POST | `/v1/webhooks/reels/{provider}` | raw body | 204 | `Mux-Signature` HMAC over the raw body, 5-minute tolerance, deduplicated |
| GET | `/v1/admin/reels/queue` | `cursor`, `limit` | `Page<QueueEntry>` | Moderator/admin; review playback tokens last 15 minutes |
| POST | `/v1/admin/reels/{id}/decision` | `{decision, reason_code, note?}` + Idempotency-Key | `{reel_id, status}` | Audited; `403 self_review`; `409 illegal_moderation_transition` |
| GET | `/v1/admin/reels/analytics` | `?days≤90` | `ReelsAnalytics` | Admin, finance or moderator; includes reel-attributed calls |

**`Reel` shape:**

```json
{
  "id": "…", "caption": "…", "language": "hi", "duration_ms": 21000, "status": "published",
  "creator": {
    "user_id": "…", "display_name": "…", "photo_url": "…|null", "followed_by_me": true,
    "host": {"availability": "online|busy|offline", "rate_per_minute": 1500, "is_verified": true} | null
  },
  "rejection_code": null, "like_count": 4, "view_count": 9, "share_count": 1,
  "liked_by_me": false, "is_mine": false,
  "playback": {"hls_url": "https://stream.mux.com/<id>.m3u8?token=…", "thumbnail_url": "…", "expires_at": "…"} | null,
  "published_at": "…", "created_at": "…"
}
```

`host` is non-null **only** for approved hosts. It is the only thing that enables the call button, and the call itself goes through the existing `/v1/calls` flow.
